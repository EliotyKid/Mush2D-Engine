# E0: Base — engine e jogo separados — Plano de Implementação

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Separar a engine do jogo: o código atual vira `examples/iki_demo/` (funcionando igual), cada jogo descreve elementos, barras, superfícies e ações de entrada num `project.json`, a entrada passa a ser por ações (teclado e gamepad), e nasce o modelo `games/ikigai/`.

**Architecture:**
- Cada jogo é uma pasta (`examples/<id>/` ou `games/<id>/`) com `project.json`, `assets/` e `src/<id>/`, compilada como biblioteca estática por uma função CMake `mush2d_add_game`. O executável de desenvolvimento `Mush2D` tem a tabela dos jogos compilados, uma tela de escolha e `--game <id>`.
- A engine ganha `Project` (lê o `project.json`, guarda o projeto ativo), nomes de elemento e de barra como `std::string`, superfícies como índice numa tabela do projeto, e `ActionMap` (ações ligadas a teclas e ao gamepad pelo GLFW).
- A abordagem é a A do spec: mover primeiro, depois trocar um vazamento por vez, com o `iki_demo` rodando ao fim de cada task.

**Tech Stack:** C++20, Vulkan 1.3, GLFW 3 (`glfwGetGamepadState`), nlohmann_json, Dear ImGui, CMake ≥ 3.24 + Ninja, MkDocs.

**Spec:** [docs/superpowers/specs/2026-11-26-e0-base-design.md](../specs/2026-11-26-e0-base-design.md). As "Escolhas do Claude" 1–5 são obrigatórias, com o ajuste do registro de tipos descrito na Task 1.

## Global Constraints

- `src/engine/**` nunca inclui nada de `examples/` nem de `games/`, e nunca cita Iki, Ikigai, kaa, gelo/ice nem fogo/fire (nem em comentários, nem em valores padrão).
- **Comentários:** todo código novo ou mexido explica, em frases curtas em inglês, o que cada função, bloco ou linha não óbvia faz. O autor é iniciante em C++ e aprende lendo o código.
- O `iki_demo` mantém a sensação de jogo: tempos de pulo (coyote 0,1 s, buffer 0,12 s), combate, peso e câmera iguais.
- `examples/iki_demo/assets/levels/showcase.ldtk`: só muda de pasta, sem mudar nenhum byte. Os caminhos relativos para os tilesets continuam válidos (a pasta `kaa/` vai junto).
- Todo número novo de jogo (buffer, limite do gatilho, zona morta, barras) é ajustável no F1.
- Gamepad só pelo GLFW (`glfwGetGamepadState`, mapeamento padrão). Nenhuma dependência nova.
- Zero erros de validação do Vulkan; a saída de validação vai para stdout. A saída de `mush2d_tests` fica limpa: avisos esperados são capturados.
- Build e testes no Linux (GCC 16) e no Windows (MSVC). Código que um só dos dois aceita é bug.
- Commits só com a autorização do autor, no branch `feat/e0-base`. Mensagens terminam com uma linha em branco e `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Nada de `git stash`.
- Ambiente Arch: `cmake --preset debug && cmake --build build/debug && ctest --test-dir build/debug --output-on-failure`.
- Cada task atualiza a página do manual que ela afeta. A Task 9 escreve as páginas novas e confere o `mkdocs build --strict`.

## Review Focus

1. **Gamepad conectado ou desconectado no meio do jogo:** sem travar e sem botão preso. Uma ação segurada no controle é solta no frame em que ele some. Teste `actions_gamepad_disconnect_releases` (Task 5).
2. **Teclado e gamepad na mesma ação ao mesmo tempo** (por exemplo, segurar `Z` e apertar `A`): um só `pressed`, e o `released` só quando os dois soltam. Teste `actions_two_sources_one_press` (Task 5).
3. **`project.json` com erro de digitação durante o hot reload:** aviso com o arquivo e o campo; o projeto anterior continua valendo e o jogo não fecha. Teste `project_bad_reload_keeps_previous` (Task 2).

  - `int keyByName(std::string_view);` e `int gamepadButtonByName(std::string_view);` devolvem `-1` para um nome desconhecido.
    - Teclas: nomes do GLFW sem prefixo (`"Z"`, `"Left"`, `"Space"`, `"LeftShift"`...).
    - Botões: `A B X Y L1 R1 Back Start Guide LeftStick RightStick DpadUp DpadRight DpadDown DpadLeft`.
    - Eixos: `L2`, `R2` (gatilhos) e `LeftStickLeft/Right/Up/Down`, `RightStickLeft/Right/Up/Down`.
  - `struct RawInput { std::array<bool, GLFW_KEY_LAST + 1> keys{}; bool padConnected = false; std::array<bool, GLFW_GAMEPAD_BUTTON_LAST + 1> padButtons{}; std::array<float, GLFW_GAMEPAD_AXIS_LAST + 1> padAxes{}; };`.
  - `struct ActionState { bool down = false, pressed = false, released = false; };`.
  - `class ActionFrame`:
    - `const ActionState& get(std::string_view) const;`: uma ação desconhecida devolve um estado parado e avisa uma vez por nome;
    - `bool down(std::string_view) const;`, `bool pressed(std::string_view) const;` e `bool released(std::string_view) const;`;
    - `glm::vec2 stick() const;`: o analógico esquerdo depois da zona morta, de -1 a 1;
    - `void keepEdges(const ActionFrame& earlier);`: mesma regra do `keepEdges` de hoje, para todas as ações;
    - `enum class Device { Keyboard, Gamepad }; Device lastDevice() const;`, para a E8.
  - `class ActionMap`:
    - `void configure(const std::map<std::string, ActionBinding, std::less<>>&, const InputSettings&);`;
    - `void update(const RawInput&);`;
    - `const ActionFrame& frame() const;`;
    - `float bufferWindow(std::string_view) const;`.
  - `GlfwInput::readRaw()` devolve `RawInput`. Com a interface bloqueada (`keyboardBlocked`), as teclas ficam soltas. O gamepad é o primeiro joystick com `glfwJoystickIsGamepad`.
- **Regras:**
  - uma ação está `down` se qualquer fonte dela está apertada;
  - um eixo conta como apertado quando passa do limite (`triggerThreshold` para gatilhos, `stickDeadzone` para os direcionais do analógico);
  - `pressed` e `released` vêm da mudança do `down` agregado, então duas fontes juntas dão um só `pressed`;
  - quando o gamepad some, todas as fontes dele ficam soltas.
- **Formato no `project.json`:**

```json
"input": { "triggerThreshold": 0.5, "stickDeadzone": 0.25 },
"actions": {
  "moveLeft":  { "keys": ["Left"],  "gamepad": ["DpadLeft", "LeftStickLeft"] },
  "jump":      { "keys": ["Z"],     "gamepad": ["A"], "buffer": 0.12 }
}
```
